# Global rules

- Work inside the current repository. Do not change files outside it unless the task says so.
- Never `git push`, open or merge a pull request, or change CI, secrets or deployments unless the task explicitly asks for it. Pushing and PR creation ask for confirmation; merging is never yours.
- Commit messages follow Conventional Commits with a scope, e.g. `fix(api): ...`. Commit with the git identity that is already configured.
- Never add AI attribution anywhere: no `Co-authored-by` or session trailers, no "generated by" notes in commits, PRs, issues or comments.
- Code comments: almost none. Only a single short line when a non-obvious reason would otherwise be lost. No comments that restate code, narrate steps or reference the task.
- Match the surrounding code's style, naming and idioms. Follow the repository's own `AGENTS.md` when it is stricter.
- Run the repository's checks (tests, linters, formatters) before calling work done, and report what you ran and the result.
- If you are blocked or the task is ambiguous, say so and stop rather than guessing broadly.

# How to work

- Discipline skills apply whenever their situation comes up: `brainstorming` before designing something new, `writing-plans` before multi-step work, `test-driven-development` for every behaviour change, `systematic-debugging` for every bug, `verification-before-completion` before claiming anything is done, `receiving-code-review` when handling review feedback.
- Subagents: `explore` to find code in this repository, `scout` for anything outside it (docs, upstream source, changelogs), `oracle` for architecture decisions, plan review and bugs that survived two fix attempts, `reviewer` after implementing and before any PR. Give a subagent the full context it needs: task, expected outcome, constraints, what not to do. Treat its report as claims to check, not as facts.
- Linear workflow (issue to PR to Done) runs through the commands `/intake`, `/refine`, `/ticket`, `/review-pr`, `/iterate`, `/close`, `/status`.
- For any task with three or more steps, keep a todo list and update it as each item is done.

# Tools

- Before running a shell command, check whether a tool covers the job; the tool wins.
- MCP tools are called from code through `execute` (code mode). Batch several calls in one script instead of one call per step.
- `context-mode` (plugin): follow its routing rules; large outputs, web fetches and data analysis go through its `ctx_*` tools so only the derived answer enters the context.
- `codegraph` (CodeGraphContext): for structure questions such as callers, callees, dependencies or impact of a change, index the repository once (`add_code_to_graph` on its root) and query the graph instead of grepping across many files.
- Shell commands are rewritten by rtk for compact output (e.g. `git status` runs as `rtk git status`). When you need the raw output, run `rtk proxy <command>`.
- `gateway`: Linear, library docs (context7) and web search (searxng).
- Linear: use the gateway's `linear-*` tools for every read and write; never scrape linear.app or guess an issue's state. The default team is Forge (issue key `XXX`). Writing to Forge issues is allowed; writing to any other team (Civora `CIV`, Routivo `ROU`, Omni `OMN`, WebDev Harke `WEB`) asks the user for confirmation, so say what you are about to write first. Never delete anything in Linear.
- GitHub: use `gh` and `git`. The workspace picks the account by repository owner (agent account for `lkshrk`, `loc-news`, `routivo`, `webdev-harke`; the personal account for other owners; fork foreign repositories under `lkshrk` with `gh repo fork`). Never call the GitHub API with curl or a token variable, and never override `GH_TOKEN`.

# Output discipline

- Keep each tool call's output small: create a large file in pieces instead of one call, and read slices of large files.
- Before a tool call, write one short line saying what you are about to do and why.
