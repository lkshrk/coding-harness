# XXX-284: One owner for issue state

Requirements: https://linear.app/h-cloud/issue/XXX-284/one-owner-for-issue-state-a-tested-transition-function-for-linear#comment-3023aa33 (approved 2026-10-10)

## Investigation

What exists today and what the feature touches.

- `packages/supervisor/src/supervisor/linear-sync.ts`: `writeStatus` and `relabel` are the two functions that write the Linear status and the `ai-stage` label. `observeIssue` keeps an in-memory `ownWrites` map so a stale read right after our own write is not taken for a change; it is lost on restart. `enforceLinear` stops every active run whose cached lifecycle is not `running`.
- Status writers (12 call sites, 8 modules), all through `writeStatus`: `dispatch.ts` (running), `pr-watch.ts` (review, done), `holds.ts` (`holdForYou` → blocked), `questions.ts` (blocked, ready), `remediation.ts` (ready), `recovery.ts` (ready for lost runs), `verification.ts` (stage and blocked), `supervisor.ts` tick (ready for unblocked dependents). Stage writers: `verification.ts` via `relabel`, and `writeStatus({ stage })`.
- Run killers on a mismatch: `LinearSync.enforceLinear` every tick and `Recovery.recoverRun` at start-up, both with reason "issue changed in Linear" and no notion of who changed the issue.
- `packages/supervisor/src/policy/stages.ts`: `decide(view)` is already a pure function from an issue view to the next supervisor action; `viewIssue` derives lifecycle, stage and awaiting. It has no notion of the actor of the last change.
- `packages/supervisor/src/ports/linear.ts`: `IssueSnapshot` carries `status`, `labels`, `updatedAt`, no actor. `LinearPort` has no history call. Linear's issue history does expose the actor; verified 2026-10-10 on XXX-245: every supervisor write shows `actor: Nightshift, app: true`.
- `packages/supervisor/src/stages/integration/stage.ts`: on an existing PR with an unchanged head it calls `pullRequestOpened`, which writes `review` again; this undid the XXX-245 retry.
- Vault pitfall `linear-complexity-budget`: Linear bills complexity by requested page size; extra reads must be small and only on demand.

## Alternatives

### A: Actor-aware observe, rules at the two killers
Keep the writers as they are. Add a `lastChange(identifier)` read to `LinearPort` (issue history, `first: 5`) and an `actor` on the snapshot, filled only when a mismatch is seen. Replace `ownWrites` by "the newest status or label change was made by the Nightshift app". Change `enforceLinear` and `recoverRun` to act per the requirements only for human changes. Patch `pr-watch`/`integration` and `ns retry` for the open-PR case.

Changes: `linear-sync.ts`, `recovery.ts`, `pr-watch.ts`, `stages/integration/stage.ts`, `dispatch.ts` (`retryRun`), `ports/linear.ts`, the Linear adapter. Small diff, no new module.

### B: One transition function, writers emit intents
Add `policy/transition.ts`: a pure `transition(current, intent, ctx) → { status?, stage?, awaiting?, runAction?, log }` with an explicit rule table. Every writer stops calling `writeStatus`/`relabel` and instead calls `applyIntent(issue, intent)`, where an intent is a named supervisor event (`dispatched`, `prOpened`, `merged`, `heldForUser`, `retryRequested`, `humanChanged(status, actor)`, …). `applyIntent` is the only code that calls `linear.update`. Human changes are detected in `observeIssue` with the history actor (as in A) and turned into a `humanChanged` intent, so the operator rules (re-queue, hold, cancel, finish) live in the same table. `enforceLinear` and the `recoverRun` check become "apply `humanChanged` if the actor is human, else re-assert our own state".

Changes: new `policy/transition.ts` + table test; the 12 writer call sites switch to intents; `linear-sync.ts` loses `ownWrites`; `recovery.ts`, `pr-watch.ts`, `integration/stage.ts`, `dispatch.ts`; Linear port and adapter as in A; a boundary test that only `applyIntent` calls `linear.update`.

## Critique

- **A:** fixes the observed incidents but keeps 12 independent writers. Acceptance criterion 5 (only one place writes status) is not met, and the next new writer can reintroduce the same class of bug. The open-PR fix stays a special case in two modules. Cheapest now, likely to regress.
- **B:** larger diff (every writer changes), and the intent list must cover every current call site or a writer will be stuck. Risk of behaviour change in modules that have tests pinned to direct status writes; those tests need rewriting to assert intents. Meets all seven criteria and makes criterion 5 checkable by a test. The extra history read happens only on a mismatch in both A and B, so cost is the same.

## Decision

Chosen: **B**, because the defect is the missing single owner (criterion 5), and A leaves it in place; the incidents are symptoms.

Rejected: **A**, because it fixes today's incidents without stopping new writers from causing the next one.

Remaining risks and how they are caught:
- An intent missing for an existing call site → the boundary test fails while any module still calls `writeStatus`/`relabel`/`linear.update` outside `applyIntent`.
- Behaviour drift in existing flows → the existing supervisor test suite (1445 tests) must pass unchanged in its assertions on Linear state; only how writes are made changes.
- History read cost → one `history(first: 5)` per detected mismatch, behind the existing complexity tracing; a test counts calls in a tick with no mismatch (must be zero).
- The operator using a Nightshift-app script is treated as the supervisor → documented constraint; `ns` commands are the operator path.

Implementation order (for `decompose`):
1. Linear port: `lastChange(identifier)` with actor and `app` flag; adapter and fake.
2. `policy/transition.ts` with the rule table and a table test over every intent × lifecycle state; no callers yet.
3. `applyIntent` in the supervisor and the boundary test; move writers to intents module by module (dispatch, PR watch and integration, holds and questions, remediation and recovery, verification and tick).
4. Actor-aware `observeIssue`; `enforceLinear` and `recoverRun` act through `humanChanged`; remove `ownWrites`.
5. `retryRequested` from `integration` with an open PR: back to `implementation`, continue from the PR head, PR watch keeps the status while the run is active.
6. One regression test per incident in the requirements' Why list.
